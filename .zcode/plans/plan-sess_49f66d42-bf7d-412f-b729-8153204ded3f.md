## Goal
After a successful customer or staff login, persist the session in SharedPreferences so a force-stop + reopen lands the user directly on the right home screen. If the persisted user no longer exists in Supabase, fall back to the role-selection screen.

## Approach (mirrors `ThemePreferences` style — no new dependency)

Add a new `SessionPreferences` singleton in `data/auth/` that mirrors the existing `ThemePreferences` pattern (same `neko_eco_prefs` file, same `init(context)` guard, same `StateFlow` exposure). `MainActivity` collects the session state and chooses `startDestination` accordingly.

## Files to change

### 1. NEW — `data/auth/SessionPreferences.kt`
- Singleton with `private lateinit var prefs: SharedPreferences`.
- Fields `session_role` ("customer" | "staff" | absent) and `session_id` (customer email or staff id).
- Synchronous `init(context)` reads prefs, populates a `MutableStateFlow<SessionState>` (`Loading | LoggedOut | LoggedInCustomer(email) | LoggedInStaff(staffId)`).
- Public `StateFlow<SessionState>` for `MainActivity` to collect.
- Methods: `persistCustomer(email)`, `persistStaff(staffId)`, `clear()`. All synchronous.

## Edge cases handled
- User logs out → next launch is `role_selection` (session cleared on logout).
- User deletes account in DB while logged out → re-auth on launch fails → session cleared, fall back to role_selection.
- User changes password → next session restore fails (account exists but old email still maps to them, but `currentCustomer`/`currentStaff` won't be re-seeded without a password — we rely on the customer/staff login to do password verification, so we'll fall back to role_selection).
- Process killed mid-login → nothing persisted, falls back to role_selection.

## Out of scope (explicitly)
- No EncryptedSharedPreferences — keeps zero new dependencies. Password is never stored, only email/staffId; re-auth proves the session still works.
- No "remember me" toggle per your answer — every successful login persists, every logout clears.
- No changes to `ThemePreferences` or its file format.
- No changes to the existing in-memory `currentCustomer` field — it remains the in-memory source of truth during the session.
